## 2. 绝对禁止的操作

不论故障多严重，都不要执行：

```bash
# 禁止：全局或批量删除
docker rm -f $(docker ps -aq)
docker container prune
docker image prune
docker volume prune
docker network prune
docker system prune
docker system prune -a --volumes

# 禁止：删数据卷或全局 Docker 数据
docker compose down -v
rm -rf /mnt/storage/docker_dir
rm -rf /mnt/storage/opt
rm -rf /mnt/storage/data

# 禁止：修改全局 Docker 配置/服务
sudo systemctl restart docker
sudo systemctl stop docker
sudo systemctl daemon-reload
sudo vi /etc/docker/daemon.json

# 禁止：在离线交付机联网拉取或就地编译
docker pull ...
docker compose pull
docker build ...
docker compose build
```

也不要对项目根目录、Docker Root Dir 或持久化数据执行递归 `chmod`/`chown`。
权限故障只能修正经过确认的单个配置或密钥文件。

## 5. RWLayer 故障的决策流程

Docker 报错 `RWLayer ... is unexpectedly nil` 意味着容器元数据仍在，但它的可写层已
丢失或元数据不一致。容器可以重建，但必须先确定它属于本手册的七个项目。

### 5.1 确认容器归属

```bash
BROKEN_CONTAINER='product-weknora-app'   # 换成报错的精确名称

docker inspect "$BROKEN_CONTAINER" \
  --format 'name={{.Name}} project={{index .Config.Labels "com.docker.compose.project"}} service={{index .Config.Labels "com.docker.compose.service"}} image={{.Config.Image}} status={{.State.Status}}'
```

允许的 Compose 项目名只有：

```text
product-weknora
product-langgraph-task-manager-dev-cjy
product-agent-toolbox
product-entity-graph
watchsystem-db-qa
product-rule-base
product-qwen3-embedding
```

如果 `project` 不在上表中，禁止删除该容器。

### 5.2 确认持久化挂载

```bash
docker inspect "$BROKEN_CONTAINER" \
  --format '{{range .Mounts}}{{println .Type .Source "->" .Destination}}{{end}}'
```

挂载源必须是本手册第 9 节列出的本项目专属数据目录或配置文件。如果指向
未识别的共享路径，停手确认。

### 5.3 只删除一个精确损坏容器

先在第 6 节备份配置，再执行：

```bash
docker rm -f "$BROKEN_CONTAINER"
```

不能使用通配符、`$(docker ps ...)` 或批量删除。删除后，到对应项目目录按第 9 节
用固定镜像重建该 service。

## 7. 镜像恢复通用规则

1. 先查 `docker image inspect <固定标签>`。
2. 镜像存在时不重复导入。
3. 镜像缺失时，先校验本地 tar，然后 `docker load -i <精确 tar>`。
4. 校验失败的 tar 禁止导入；从本机保留的已验证离线包重新复制。
5. 禁止使用 `latest`、`pull`、`build` 或覆盖现有版本标签。

通用检查：

```bash
docker image inspect '<image>:<fixed-version>'
docker load -i '/absolute/path/to/image.tar'
docker image inspect '<image>:<fixed-version>'
```

## 8. 端口冲突的处理

恢复前检查目标端口：

```bash
ss -ltnp | grep -E ':(9750|9751|9753|9754|9757|9758|7474|7687|9890|9780|9781|9782|9704|9705|9706|9707|5670|5671|9700|9701|8011)\b'
```

如果端口由本项目现有容器占用，是正常现象。如果由任何其他进程/容器占用：

- 立即停止该项目的启动。
- 不停止、不重启、不删除占用者。
- 记录 `ss -ltnp` 和 `docker ps --filter publish=<port>` 结果后升级处理。

## 11. WeKnora 401/409 认证排查

当其他平台调用 `/api/v1/sessions` 出现 `401 Unauthorized`，先确认后端请求同时包含：

```http
X-API-Key: <WEKNORA_API_KEY>
X-Tenant-ID: 10000
```

只读验证：

```bash
curl -sS 'http://192.168.18.36:9751/api/v1/sessions' \
  -H 'X-API-Key: <WEKNORA_API_KEY>' \
  -H 'X-Tenant-ID: 10000'
```

| HTTP 状态 | 含义 |
|---|---|
| 200 | API Key 和 Tenant ID 有效 |
| 401 | API Key 缺失、错误、失效或被代理删除 |
| 409 `TENANT_REQUIRED` | API Key 已识别，但没有传 `X-Tenant-ID` |
| 403 | Tenant/权限与目标资源不匹配 |

长期 API Key 明文只保存在本机的《18.36 七项目离线目录与资料总索引》中。
不要把它写到远程 shell 历史、截图或客户端代码。

## 12. 密钥、密文和权限故障

### 12.1 密钥丢失或不匹配

典型表现是启动时报 `E1001/E1002/E1003/E1004`、AES-GCM authentication failed 或
“encrypted configuration value could not be decrypted”。

处理顺序：

1. 不生成新密钥。
2. 核对 Compose 挂载的密钥路径。
3. 核对 `runtime.env`/`.env` 和 `master.key` 是否来自同一个备份。
4. 从同一 `recovery-<timestamp>` 备份成对恢复。
5. 只重建本项目容器。

远程正式配置必须保持 `ENC(...)`/`ENC(v1:...)`；不得将本机私密索引中的明文
整段复制到服务器。

### 12.2 权限错误

先只读检查：

```bash
stat -c '%a %U:%G %n' /absolute/path/to/runtime.env /absolute/path/to/master.key
```

`runtime.env` 和 `master.key` 通常应为 `600`。如需修正，只修正确认的单文件：

```bash
chmod 600 /absolute/path/to/runtime.env
chmod 600 /absolute/path/to/master.key
```

所有者需与 Compose 内镜像 UID 匹配；不要根据用户名观感擅自 `chown`。例如 WeKnora
密钥由容器 UID 使用，宿主机显示的用户/组名可能不直观，但不代表配置错误。
